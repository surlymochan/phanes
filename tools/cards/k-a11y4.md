## Findings (from an audit written before the upstream sync; references may have moved)

### 6. The routine status in the planner list is not exposed

**Evidence**

- `packages/ui/src/features/conversation/RoutineCalendar.tsx:609-626`: `RoutineCalendarStatusMark`
  is `aria-hidden="true"`.
- `packages/ui/src/features/conversation/RoutineCalendar.tsx:565`: the entry button carries
  `aria-label={t("routine.card.open", { name })}`. That key is "Open routine {name}"
  (`packages/i18n/src/messages/en/routine.ts:161`).
- `packages/ui/src/features/conversation/RoutineCalendar.tsx:572-576`: the visible status text sits
  in `routine.calendar.entryMeta` ("{when} · {schedule} · {status}",
  `packages/i18n/src/messages/en/routine.ts:190`). The `aria-label` replaces it.
- `packages/ui/src/features/conversation/RoutineCalendar.tsx:430-433`: the day view in the same file
  does put the status in its label.

**Why it matters**

A screen reader user cannot tell a failed run from a completed one in the "upcoming" list. The
colour and the icon carry the state for a sighted user. This breaks WCAG 1.3.1 Info and
Relationships (level A) and WCAG 4.1.2 (level A).

**Fix**

Add the status to the entry `aria-label`, as the day view does. Or remove the `aria-label` and let
the visible name and the meta line form the name.

**Size** S.

### 7. Five `role="toolbar"` elements do not move the focus with the arrow keys

**Evidence**

- `packages/ui/src/features/conversation/SelectionActions.tsx:382`
- `packages/ui/src/features/conversation/MessageRendering.tsx:647`
- `packages/ui/src/features/conversation/DiagramCanvas.tsx:179`
- `packages/ui/src/features/diagrams/DiagramBoard.tsx:683`
- `src/renderer/src/features/browser/browser-pip-controls.tsx:23`

**Why it matters**

The ARIA toolbar pattern says that the arrow keys move the focus between the controls of the
toolbar. Here the arrow keys do nothing. A screen reader user reads the role, expects arrow-key
navigation, and does not get it. This breaks WCAG 4.1.2 Name, Role, Value (level A).

**Fix**

Add a roving tabindex and an arrow-key handler to each toolbar. The two zoom toolbars have three
buttons each and are the easiest. For the selection and message toolbars, a shared helper in
`packages/ui/src/utils.ts` keeps the behaviour the same.

**Size** M for the five. S for one.

### 8. The focus order in onboarding does not match the visual order

**Evidence**

- `src/renderer/src/features/onboarding/onboarding.css:371-373`: `.onboarding-next { order: -1; }`.
- `src/renderer/src/features/onboarding/FirstRunFlow.tsx:362-372`: the DOM order is the Back button
  and then the Next button.

**Why it matters**

CSS `order` moves the Next button to the left on screen, but the DOM order and the tab order stay
as they are. A keyboard user presses `Tab` on the first step and lands on the visually second
button. This breaks WCAG 2.4.3 Focus Order (level A).

**Fix**

Remove `order: -1` and put the Next button first in the DOM. The visual result stays the same, and
the two orders agree.

**Size** S.
