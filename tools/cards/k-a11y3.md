# M10 #62: selection toolbar focus and tab roles (a11y 4-5)

Repository: OpenBot desktop (Electron, Bun, TypeScript, SolidJS). Read AGENTS.md and the AGENTS.md of every directory you change, and follow them.

## Scope

Accessibility findings 4 and 5 below. Your base already contains your fixes for findings 1, 2, 3 and 15. Keep visuals and mouse behavior unchanged.

## Findings (from an audit written before the upstream sync; references may have moved)

### 4. The selection toolbar is the last stop in the tab order, and it never takes focus

**Evidence**

- `packages/ui/src/features/conversation/SelectionActions.tsx:355`: the toolbar renders in a
  `Portal`, so it lands at the end of `document.body`, after the whole application.
- `packages/ui/src/features/conversation/SelectionActions.tsx:373-390`: the layer and the
  `role="toolbar"` element.
- `packages/ui/src/features/conversation/SelectionActions.tsx:161-176`: the open path listens for
  `pointerup` and `keyup`. It never calls `focus()`.
- `packages/ui/src/features/conversation/SelectionActions.tsx:170-176`: only the Quote action has a
  keyboard shortcut. Explain, Improve, Shorten, Tone and Grammar have none.

**Why it matters**

A user who selects message text with `Shift+Arrow` gets a floating toolbar. The toolbar sits at the
end of the document, so the next `Tab` press does not go there. The user must tab through the rest
of the application to reach the actions. The feature is pointer-only in practice. This breaks
WCAG 2.1.1 Keyboard (level A) and WCAG 2.4.3 Focus Order (level A).

**Fix**

When the toolbar opens, move the focus to the first control in the bar. When it closes, put the
focus back on the message that held the selection. The toolbar already keeps its own state
(`packages/ui/src/features/conversation/SelectionActions.tsx:88-95`), so the two focus moves fit
there.

**Size** M.

### 5. Six views expose `role="tab"` with no tab panel

**Evidence**

Kobalte renders `role="tab"` and `aria-controls` on a trigger
(`node_modules/@kobalte/core/dist/tabs/Bcy3rD0-.js:352,365`). Only `Tabs.Content` renders
`role="tabpanel"` (`node_modules/@kobalte/core/dist/tabs/Bcy3rD0-.js:106`). These files use a
trigger and never a content:

- `packages/ui/src/components/GlobalSearch.tsx:871-876`
- `packages/ui/src/features/browser/BrowserTabStrip.tsx:363-456`
- `packages/ui/src/features/conversation/SidePanel.tsx:132-227` — the comment at lines 114-118 says
  that no tab panel is registered
- `packages/ui/src/features/sidebar/SidebarViewSwitch.tsx:19-35`
- `packages/ui/src/features/conversation/RoutineCalendar.tsx:313-322`
- `packages/ui/src/features/conversation/SkillLibraryToolbar.tsx`

**Why it matters**

The selected tab gets an `aria-controls` value that points to no element. A screen reader says
"tab" and then has no panel to move to. The global search filter pills are the worst case: they
filter one listbox, and a tab pattern says that the content changes in a panel. This breaks
WCAG 4.1.2 Name, Role, Value (level A).

**Fix**

For the global search, use `role="radiogroup"` with `role="radio"` for the filter pills. They are
one choice out of many. For the browser tab strip and the side panel, either register a
`Tabs.Content` region for each pane, or drop the tab pattern and use a plain button with
`aria-pressed` or `aria-current`. `SidebarViewSwitch`, `RoutineCalendar` and `SkillLibraryToolbar`
can follow the same route.

**Size** M.
