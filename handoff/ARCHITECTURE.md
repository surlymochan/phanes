# Phanes 架构

> **唯一权威的详细架构文档。** 其他文档只能引用本文，不得另写一份架构描述。任何架构调整都必须更新本文，并在“演进记录”追加条目。

**结论：** Phanes 采用 Boss/Router 统筹、swrm 执行、事件汇总唤醒、独立质量门禁和证据留存的协作架构。本文把已实现能力与设计目标分开；“已上线”仅表示仓库存在对应实现，不代表生产部署或端到端验收已经完成。

状态：整理于 2026-11-08。swrm 新版已部署到全部 8 台主机；运行时配额和端到端交付仍按正文标注状态。

## 1. 现状（已上线）

### 1.1 角色与责任边界

| 角色 | 已上线职责 | 状态与边界 |
|---|---|---|
| Boss（Router） | 定方向、做裁决、批准预算与风险边界、审核部署；将执行、诊断、脚本编写和部署任务派成卡 | 统筹角色；不作为常规执行器。控制面目前处于过渡期，临时承担部分执行，尚未完全分离 |
| Watchdog | 定时巡检，并可执行预先限定的运维动作 | 具体巡检项、动作白名单和线上运行情况未在本仓库验证 |
| swrm（命令 `swrm`） | 一次性 `run` 和常驻 `lane` 两种执行形态；协调作者与审查任务，记录运行状态和产物 | 唯一来源已并入；新版已部署到全部 8 台主机，真实交付链仍需按任务验收 |
| evalid 角色 | `evalid-spec`、`evalid-tdd`、`evalid-review` 在 evalid、swrm 与控制面间传递声明、证据及门禁状态 | 实现已贯通；派发开关默认关闭，待真实环境端到端验收 |
| 控制面 | 编排 evalid 角色状态机、冻结 intake、管理私有 holdout 收据，并只公开白名单状态 | 实现已合并；角色派发默认关闭，待真实环境端到端验收 |
| Volto | 桌面应用；仓库目录名由 openbot 改为 volto | 改名已合并；持久运行身份保留 |
| 独立 Reviewer | 对固定提交链审查，并运行受控检查、保留测试及行为差分 | 工具和门禁规则已存在；各项目是否始终覆盖完整提交链未验证 |

**仓库归属**：phanes 为唯一来源仓库。swrm（#1894）和 evalid（#1893）已并入 phanes；swrm 同步上游 `watch --wake`、`--scope host` 与 Windows 修复（#1897），结果分支前缀为 `swrm/`。openbot 在仓库内改名 volto（#1895），持久运行身份保留。开发/测试 Electron 使用 mock keychain（#1899）。

### 1.2 执行层、容量与模型

| 项目 | 当前事实 / 约束 | 状态 |
|---|---|---|
| 执行位置 | 控制面原则上不执行任务，执行分摊到其他机器；过渡期控制面仍临时承担部分执行 | 目标边界已确定，迁移未完成 |
| 容量上限 | policy、topology、host 三层共同限制容量；任何上限调整必须三处一致并复核生效值 | 控制面 host 并发上限 2；中继与网关节点各最多 2 个 lane，总计 20 个 lane |
| 作者模型白名单 | Build 作者 50% `MiniMax-M3.1-Flash` + 50% `gpt-6-luna` high；MiniMax 不可用时由 agy 补位 | 规则已记录；实际每次运行需核对回执 |
| Reviewer 模型 | 只用 `gpt-6.1-terra` high | 规则已记录；6.1 系列依赖付费订阅，实际每次运行需核对回执 |
| Spec 模型 | `gpt-6.1-sol` high | 规则已记录；6.1 系列依赖付费订阅，实际每次运行需核对回执 |
| 修复升级 | 修复轮次按 `sol` medium → `sol` high → Boss 裁定逐级升级 | 规则已记录；升级判定与实际轮次记录需核对 |
| 总并发 | 中继与网关节点各最多 2 个 lane，共 20 个 lane | 配额规则已记录；仍以运行环境实际生效配置为准 |
| 单机执行槽 | 控制面 host 并发上限 2 | 配额规则已记录；仍以运行环境实际生效配置为准 |

运行时配额以三层实际配置及 swrm 回执为准。不得把模型选择规则或本仓库默认值当成每次运行已生效的事实。

### 1.3 事件层

已上线的基本链路为 **swrm 运行事件汇总 → eventd → 消费者唤醒**。swrm 已同步上游 `watch --wake` 并支持 `--scope host`。eventd 有规则分类、Decisions API 决策、失败兜底唤醒、消费者分组及各消费者独立规则/覆盖与静音、独立游标和日志恢复能力。唤醒应携带事件 ID、摘要和指针，统筹会话据此读取原始记录；不把整段运行日志当作唤醒正文。

交付语义是**至少一次**：消费者可能收到重复事件，须按游标或稳定 ID 去重。stdout 输出与游标提交无法跨系统原子化；当前协议没有消费者 ACK。eventd 的仓库实现存在，但实时部署、统筹会话自动恢复及完整事件链的线上验收状态未知。

### 1.4 质量证据与评审门禁

- `evalid` 已并入 phanes；evalid-spec / evalid-tdd / evalid-review 三个声明式角色已贯通 evalid、swrm 与控制面（#1898）。控制面负责角色状态机、intake 冻结、私有 holdout 收据及白名单公开状态，依赖 `tools/evidence.py`、`tools/review_run.py`。角色派发开关默认关闭，待真实环境端到端验收。
- 独立审查覆盖整个提交链，审查输入关联 Issue/Spec、验收条件和固定版本；受影响提交变动后须重新审查。
- **BLOCKER**：违反明确验收条件；正常输入下崩溃或结果错误；数据丢失/损坏；明显安全问题；或提交混入任务范围外文件。未解决的 BLOCKER 不放行。
- **FOLLOW-UP**：不违反明确验收条件且不导致上述严重后果的额外边界、测试、风格或优化事项，记录后续处理，不阻断当前放行。
- PASS/FAIL 必须能回溯到保留测试、审查意见和 evalid 证据。工具存在不等于每个任务都已产生有效证据；覆盖率与端到端门禁执行情况未验证。

## 2. 目标（设计中）

### 2.1 角色、执行和容量

Boss 作为 Router，只做方向、裁决、预算与风险边界审批、部署审核；所有具体执行、诊断、脚本编写和部署都形成任务卡并由执行层完成。Watchdog 定时巡检，只执行明确限定的运维动作；超出动作白名单的事项提交统筹裁决。

执行层通过 swrm 提供一次性 run 和常驻 lane。控制面完成执行迁移后不承载任务执行，任务分布到执行机、模型代理机、实验机等角色节点。容量以 policy、topology、host 三层交集为准，三处配置必须一致；中继与网关节点各最多 2 个 lane，总计 20 个 lane；控制面 host 并发上限为 2。作者、审查、Spec 模型及修复升级路径分别遵守 §1.2 白名单。国内执行机访问模型 API 与 GitHub 的出网路径见 §1.6。上线前以及每次变更后读取实际配置与运行回执，不能仅依赖文档值。

### 2.2 事件驱动闭环

```text
swrm 事件汇总
      ↓
eventd：规则层 → Decisions API 决策层 → 失败/超时兜底
      ↓ 按消费者分组；应用覆盖与静音
消费者收到：事件 ID + 摘要 + 原始记录指针
      ↓ 至少一次投递，消费者去重
统筹会话被唤醒并读取原始记录、更新任务状态
```

每个消费者独立管理分组、规则、覆盖/静音与游标。决策不可用、超时或规则无法安全确定时走唤醒兜底。恢复应从持久化事件和 runs 重建状态；重复投递不得重复执行有副作用的动作。

### 2.3 自动化流水线

| 流水线 | 目标职责 | 必须遵守的边界 |
|---|---|---|
| L2 泵 | 实现 → 复现门禁 → 结构化 REPORT 分流 → 续跑 → 独立审查 → 有界自动修复；从 runs 重建当前状态 | 状态真值来自 runs 和原始证据，不以临时队列/缓存作为完成依据；复现失败与作者失败分开归类；修复模型按 `sol` medium → `sol` high → Boss 裁定升级（见 §1.2） |
| PR 泵 | 管理推送前检查、PR 生命周期与后续修复 | 推送和合并前校验文件清单、HEAD 与预期基线；输出脱敏；PR 后续事件回流原批次；自动修复轮数有上限，超限交统筹 |
| janitor | 压缩日志、清理过期 worktree、清理孤儿进程、回收泄漏的容量预留 | 只清理可判定为过期且无活动所有者的资源；保留可审计记录，容量回收以协调器状态为准 |

上述流水线为设计目标；各项在真实环境中的自动执行、故障恢复和审计闭环尚未整体验收。

### 2.4 质量门禁与 L1 评估

独立 Reviewer 检查整个提交链及其与 Spec 的一致性。提交链中出现无关文件一律为 BLOCKER。审查方给出 BLOCKER/FOLLOW-UP 分级，并链接固定提交、保留测试结果和 evalid 证据；作者提交新版本后，审查方针对受影响部分复核。

L1 指标口径：

- **首轮通过** = 首次评审放行，且冻结的保留测试通过。
- **保留测试是真值，评审是门禁。** 评审放行不能覆盖保留测试失败；评审拒绝也不能伪装成保留测试失败。
- 实验须隔离作者与保留测试/参考真值；隔离不成立的样本单列，不并入有效 L1 分母。
- 基础设施失败（包括模型服务错误）不计入作者成功/失败分母，应单列并按预先定义的规则重跑。
- 实验开始前冻结任务卡、Spec、保留测试、模型、隔离条件和统计口径；报告原始样本与排除原因，不从失败样本中事后挑选口径。

以上为统一评估设计；隔离是否满足及 L1 数据是否满足该口径，逐批次核验。

截至 2026-11-08 08:30，L1 有 38 个有效样本，首轮通过率 81.6%（目标 ≥50%），三轮内通过率 89.5%（目标 ≥90%，尚差一个样本）；按隐藏测试真值计分。该数据对应本批次，不能替代后续批次独立核验。

### 2.5 目标交付流程

```text
Issue → Spec（BDD）→ Build（BDD 转 TDD）→ Reviewer（对照证据和 Spec）
```

1. Issue 给出问题、边界和背景。
2. 独立 Spec 步骤补齐可执行的 BDD 场景、常量、退出码、输出格式、边界与验收命令，并经独立核对后放行。
3. Build 将 BDD 场景转成失败测试，再实现到通过；作者测试证明实现符合场景。
4. 独立 Reviewer 只读固定提交链，对照 Spec、保留测试及 evalid 证据给出 PASS/FAIL 和 BLOCKER/FOLLOW-UP。

上述三步分别对应已贯通的 evalid-spec / evalid-tdd / evalid-review 三个声明式角色（见 §1.1、§1.4）；角色派发开关默认关闭，真实环境端到端验收待完成。

目标流程跟踪 Issue：[#1885](https://github.com/surlymochan/phanes/issues/1885)。快速路径的适用判据、完整流程部署和效果仍待验证。

### 2.6 需求追溯

Issue、Spec、任务运行、固定提交、测试证据、审查结论及 PR 必须可相互追溯。每个 PR 关联 Issue；验收针对固定版本，审查后的相关改动必须复核。合入由 Router 审核。项目字段映射及真实仓库中的自动约束以实际配置核验，本文不代替运行证据。

## 3. 运维和变更原则

- 模型、总并发、隔离和自动修复上限属于策略约束；改动需记录依据、验证结果和回滚方式。
- 组网与出网变更（Headscale/Tailscale 节点、网关监听地址与转发、SSH 别名）按 §1.6 记录，变更后验证组网地址可达与出网路径；记录只用角色名。
- 任何架构内容调整都更新本文并追加 §4 演进记录；ROLES、PROTOCOL 与 HANDOFF 只写操作规则并链接对应章节。
- 对未验证的能力明确标为未验证；排队、接收或单元测试通过均不等于端到端运行成功。
- **防线落在边界**：放行类防线（越界文件、废弃目录、验收证据）必须在仓库边界（CI、分支保护）生效；派发组件内的检查只算提前拦截。替换控制面组件时，迁移清单逐条列出旧组件承载的防线，并在新路径上复验。
- **状态唯一事实源**：运行状态以执行端 run 目录的原始记录为准；镜像、缓存和快照只能补充字段，不得覆盖源字段；计数排除镜像；所有排序键对缺失值显式回退（例如 run ID 时间戳）。
- **限值语义**：每个并发或额度限值只有一个事实源，其余位置由它派生；`0` 表示禁止，只有缺失表示不限。限值改动以运行中进程的实际值和排队任务确实开始运行为验收，不以配置文件内容为验收。
- **扩容先算供给**：一个批次同一时刻只有一个 run，在跑数上限等于可推进批次数；可推进批次数低于新上限时不扩容，先补供给。批次状态机的每个终态必须定义出口（下一步、重做或上报裁定），不允许只告警的终态。
- **基线新鲜度**：派发前检查批次基线之后 main 是否删除、移动了批次涉及的路径；是则在新基线上重新复现，不在旧基线上继续实现。
- **事件契约**：事件与结果格式属于接口。生产者改格式时，同一变更内更新消费者规则和回归语料；判定优先使用结构化字段，不用自由文本子串匹配。
- **供给门槛**：开 issue 必须写明影响类别（用户可见、故障或阻塞）和受影响方；代码位置只是定位，不算影响。自动审计、AI 走查得出的问题默认进 backlog，不直接开 issue；backlog 只在合批后，或升级为有影响的问题时才出卡。
- **合批**：同一模块、同类的问题合成一张 bundle 卡，只做一次复现、一次审查、开一个 PR，PR 正文逐条列出覆盖的问题，并在合并时一起关闭。目标是每个 PR 覆盖 3–10 个微型问题；单问题 PR 只用于 M 级及以上的问题，或需要单独回滚的改动。
- **按尺寸定流程**：S 级（单模块、≤50 行、不改接口和数据格式）免独立复现与独立 Spec，由作者自带测试，用轻量审查（可用便宜模型）；M 级及以上走完整流程（复现、Spec、TDD、独立审查）。尺寸由供给方标注，审查发现超出尺寸时升级流程。验收命令、CI、越界文件检查、公开边界门禁属于安全阀，任何尺寸都不得省略（PROTOCOL §2）。
- **供给先算合并能力**：在途 PR（未合并且非草稿）超过合并能力（近 4 小时的合并数，加上当前审查与 CI 的余量）时，停止新供给，先清堵塞（BLOCKED、DIRTY、CI 失败）。这与"扩容先算供给"互为镜像：上游产出不得持续高于下游的消化能力。

### 2026-11-07 L2 流水线加入独立 Spec（BDD）与 TDD 构建

**目标流程**：Issue → Spec（BDD）→ Build（BDD 转 TDD）→ Reviewer（对照证据和 Spec）。

**依据与结论**：既有实验暴露出规格不完整、评审判断与保留测试结果不一致，以及模型服务故障混入作者失败统计等问题。原实验样本及详细数据不在本公开文档复制；基础设施失败须从质量分母中排除，结论在独立重跑前保持未验证。正式 L1 应使用冻结保留测试和预先固定的统计口径。

**角色与约束**：

1. Spec 步骤由独立 run 补齐 BDD 场景；作者不参与，Spec 经独立核对后放行。
2. Build 将场景转为失败测试，再实现至通过。
3. 保留部分场景不给作者，只用于独立审查与验收。
4. Reviewer 对照 Spec、保留测试和固定版本提交链判定 PASS/FAIL，沿用 BLOCKER 与 FOLLOW-UP 规则。
5. 简单且规格明确的 Issue 可否跳过独立 Spec，判据待定。

**状态**：设计中，未完成全链路实施与验收。模型约束见 §1.2；各次运行仍以实际回执核对模型与 effort。
