# Phanes 架构

> **唯一权威的详细架构文档。** 其他文档只能引用本文，不得另写一份架构描述。任何架构调整都必须更新本文，并在“演进记录”追加条目。

**结论：** Phanes 采用 Boss/Router 统筹、swrm 执行、事件汇总唤醒、独立质量门禁和证据留存的协作架构。本文把已实现能力与设计目标分开；“已上线”仅表示仓库存在对应实现，不代表生产部署或端到端验收已经完成。

状态：整理于 2026-11-07。未从本仓库证实的运行时部署、配额和全链路结果均标为“未验证”。

## 1. 现状（已上线）

### 1.1 角色与责任边界

| 角色 | 已上线职责 | 状态与边界 |
|---|---|---|
| Boss（Router） | 定方向、做裁决、批准预算与风险边界、审核部署；将执行、诊断、脚本编写和部署任务派成卡 | 统筹角色；不作为常规执行器。控制面目前处于过渡期，临时承担部分执行，尚未完全分离 |
| Watchdog | 定时巡检，并可执行预先限定的运维动作 | 具体巡检项、动作白名单和线上运行情况未在本仓库验证 |
| swrm（命令 `openswarm`） | 一次性 `run` 和常驻 `lane` 两种执行形态；协调作者与审查任务，记录运行状态和产物 | CLI 与执行能力已存在；完整 Phanes 交付链仍需按真实任务验收 |
| 独立 Reviewer | 对固定提交链审查，并运行受控检查、保留测试及行为差分 | 工具和门禁规则已存在；各项目是否始终覆盖完整提交链未验证 |

### 1.2 执行层、容量与模型

| 项目 | 当前事实 / 约束 | 状态 |
|---|---|---|
| 执行位置 | 控制面原则上不执行任务，执行分摊到其他机器；过渡期控制面仍临时承担部分执行 | 目标边界已确定，迁移未完成 |
| 容量上限 | policy、topology、host 三层共同限制容量；任何上限调整必须三处一致并复核生效值 | 三层配置机制存在；目标总量是否已在每个运行环境一致生效，未验证 |
| 作者模型白名单 | `gpt-6-luna` high 或 `MiniMax-M3.1-Flash` | 用户设定的约束；部署覆盖情况未验证 |
| Reviewer 模型 | `gpt-6.1-terra` high | 用户设定的约束；实际每次运行需核对回执 |
| Spec 模型 | `gpt-6.1-sol` high | 用户设定的约束；实际可用性及运行记录未验证 |
| 总并发 | 20：Codex 10、MiniMax 10 | 目标配额；仓库默认策略不等于线上有效配额，需核对 policy、topology、host 三层 |

运行时配额以三层实际配置及 OpenSwarm 回执为准。不得把模型选择意向或本仓库默认值当成正在运行的事实。

### 1.3 事件层

已上线的基本链路为 **swrm 运行事件汇总 → eventd → 消费者唤醒**。eventd 有规则分类、Decisions API 决策、失败兜底唤醒、消费者分组及各消费者独立规则/覆盖与静音、独立游标和日志恢复能力。唤醒应携带事件 ID、摘要和指针，统筹会话据此读取原始记录；不把整段运行日志当作唤醒正文。

交付语义是**至少一次**：消费者可能收到重复事件，须按游标或稳定 ID 去重。stdout 输出与游标提交无法跨系统原子化；当前协议没有消费者 ACK。eventd 的仓库实现存在，但实时部署、统筹会话自动恢复及完整事件链的线上验收状态未知。

### 1.4 质量证据与评审门禁

- `evalid` / 证据工具可记录测试命令、固定代码版本和运行结果，并验证留存记录。
- 独立审查覆盖整个提交链，审查输入关联 Issue/Spec、验收条件和固定版本；受影响提交变动后须重新审查。
- **BLOCKER**：违反明确验收条件；正常输入下崩溃或结果错误；数据丢失/损坏；明显安全问题；或提交混入任务范围外文件。未解决的 BLOCKER 不放行。
- **FOLLOW-UP**：不违反明确验收条件且不导致上述严重后果的额外边界、测试、风格或优化事项，记录后续处理，不阻断当前放行。
- PASS/FAIL 必须能回溯到保留测试、审查意见和 evalid 证据。工具存在不等于每个任务都已产生有效证据；覆盖率与端到端门禁执行情况未验证。

### 1.5 当前自动化能力

| 自动化 | 仓库可确认的现状 | 未验证 / 设计边界 |
|---|---|---|
| swrm 一次性 run、常驻 lane | CLI 与运行目录能力已实现 | 两种模式在目标拓扑上的稳定性与全链路交接未验证 |
| eventd | 汇总、规则、决策、分组、游标和至少一次交付逻辑已实现 | 在线部署和统筹会话唤醒闭环未验证 |
| L2 泵 | 本仓库未找到可确认完整链路的单一实现 | 实现、复现门禁、结构化 REPORT 分流、续跑、审查、自动修复及以 runs 为准重建状态，列为目标 |
| PR 泵 | 本仓库未找到可确认完整链路的单一实现 | 推送/合并前文件清单与 head 校验、脱敏、PR 后续事件回流原批次、修复轮数上限，列为目标 |

## 2. 目标（设计中）

### 2.1 角色、执行和容量

Boss 作为 Router，只做方向、裁决、预算与风险边界审批、部署审核；所有具体执行、诊断、脚本编写和部署都形成任务卡并由执行层完成。Watchdog 定时巡检，只执行明确限定的运维动作；超出动作白名单的事项提交统筹裁决。

执行层通过 swrm 提供一次性 run 和常驻 lane。控制面完成执行迁移后不承载任务执行，任务分布到执行机、模型代理机、实验机等角色节点。容量以 policy、topology、host 三层交集为准，三处配置必须一致；目标并发为总计 20，其中 Codex 10、MiniMax 10。作者、审查、Spec 模型分别遵守 §1.2 白名单。上线前以及每次变更后读取实际配置与运行回执，不能仅依赖文档值。

### 2.2 事件驱动闭环

```text
swrm 事件汇总
      ↓
eventd：规则层 → Decisions API 决策层 → 失败/超时兜底
      ↓ 按消费者分组；应用覆盖与静音
消费者收到：事件 ID + 摘要 + 原始记录指针
      ↓ 至少一次投递，消费者去重
统筹会话被唤醒并读取原始记录、更新任务状态
```

每个消费者独立管理分组、规则、覆盖/静音与游标。决策不可用、超时或规则无法安全确定时走唤醒兜底。恢复应从持久化事件和 runs 重建状态；重复投递不得重复执行有副作用的动作。

### 2.3 自动化流水线

| 流水线 | 目标职责 | 必须遵守的边界 |
|---|---|---|
| L2 泵 | 实现 → 复现门禁 → 结构化 REPORT 分流 → 续跑 → 独立审查 → 有界自动修复；从 runs 重建当前状态 | 状态真值来自 runs 和原始证据，不以临时队列/缓存作为完成依据；复现失败与作者失败分开归类 |
| PR 泵 | 管理推送前检查、PR 生命周期与后续修复 | 推送和合并前校验文件清单、HEAD 与预期基线；输出脱敏；PR 后续事件回流原批次；自动修复轮数有上限，超限交统筹 |
| janitor | 压缩日志、清理过期 worktree、清理孤儿进程、回收泄漏的容量预留 | 只清理可判定为过期且无活动所有者的资源；保留可审计记录，容量回收以协调器状态为准 |

上述流水线为设计目标；各项在真实环境中的自动执行、故障恢复和审计闭环尚未整体验收。

### 2.4 质量门禁与 L1 评估

独立 Reviewer 检查整个提交链及其与 Spec 的一致性。提交链中出现无关文件一律为 BLOCKER。审查方给出 BLOCKER/FOLLOW-UP 分级，并链接固定提交、保留测试结果和 evalid 证据；作者提交新版本后，审查方针对受影响部分复核。

L1 指标口径：

- **首轮通过** = 首次评审放行，且冻结的保留测试通过。
- **保留测试是真值，评审是门禁。** 评审放行不能覆盖保留测试失败；评审拒绝也不能伪装成保留测试失败。
- 实验须隔离作者与保留测试/参考真值；隔离不成立的样本单列，不并入有效 L1 分母。
- 基础设施失败（包括模型服务错误）不计入作者成功/失败分母，应单列并按预先定义的规则重跑。
- 实验开始前冻结任务卡、Spec、保留测试、模型、隔离条件和统计口径；报告原始样本与排除原因，不从失败样本中事后挑选口径。

以上为统一评估设计；隔离是否满足及 L1 数据是否满足该口径，逐批次核验。

### 2.5 目标交付流程

```text
Issue → Spec（BDD）→ Build（BDD 转 TDD）→ Reviewer（对照证据和 Spec）
```

1. Issue 给出问题、边界和背景。
2. 独立 Spec 步骤补齐可执行的 BDD 场景、常量、退出码、输出格式、边界与验收命令，并经独立核对后放行。
3. Build 将 BDD 场景转成失败测试，再实现到通过；作者测试证明实现符合场景。
4. 独立 Reviewer 只读固定提交链，对照 Spec、保留测试及 evalid 证据给出 PASS/FAIL 和 BLOCKER/FOLLOW-UP。

目标流程跟踪 Issue：[#1885](https://github.com/surlymochan/phanes/issues/1885)。快速路径的适用判据、完整流程部署和效果仍待验证。

### 2.6 需求追溯

Issue、Spec、任务运行、固定提交、测试证据、审查结论及 PR 必须可相互追溯。每个 PR 关联 Issue；验收针对固定版本，审查后的相关改动必须复核。合入由 Router 审核。项目字段映射及真实仓库中的自动约束以实际配置核验，本文不代替运行证据。

## 3. 运维和变更原则

- 模型、总并发、隔离和自动修复上限属于策略约束；改动需记录依据、验证结果和回滚方式。
- 任何架构内容调整都更新本文并追加 §8 演进记录；ROLES、PROTOCOL 与 HANDOFF 只写操作规则并链接对应章节。
- 对未验证的能力明确标为未验证；排队、接收或单元测试通过均不等于端到端运行成功。

### 2026-11-07 L2 流水线加入独立 Spec（BDD）与 TDD 构建

**目标流程**：Issue → Spec（BDD）→ Build（BDD 转 TDD）→ Reviewer（对照证据和 Spec）。

**依据与结论**：既有实验暴露出规格不完整、评审判断与保留测试结果不一致，以及模型服务故障混入作者失败统计等问题。原实验样本及详细数据不在本公开文档复制；基础设施失败须从质量分母中排除，结论在独立重跑前保持未验证。正式 L1 应使用冻结保留测试和预先固定的统计口径。

**角色与约束**：

1. Spec 步骤由独立 run 补齐 BDD 场景；作者不参与，Spec 经独立核对后放行。
2. Build 将场景转为失败测试，再实现至通过。
3. 保留部分场景不给作者，只用于独立审查与验收。
4. Reviewer 对照 Spec、保留测试和固定版本提交链判定 PASS/FAIL，沿用 BLOCKER 与 FOLLOW-UP 规则。
5. 简单且规格明确的 Issue 可否跳过独立 Spec，判据待定。

**状态**：设计中，未完成全链路实施与验收。模型约束见 §1.2；各次运行仍以实际回执核对模型与 effort。
