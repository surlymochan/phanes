# Phanes 协作架构提案

状态：融合方案实施中，未完成全链路验收 · 2026-11-07

## 1. 目标与原则

Phanes 以 Boss 统筹、RSI 进化为核心，通过 swrm 异步调度执行与审查，用 evalid 固化测试证据，并以 GitHub Projects、Issue 和 PR 串联需求到交付。

Boss 默认只做统筹、派单和验收。可拆分的实现、测试、排障、资料整理和常规核查，优先交给 swrm lane、临时 subagent 或脚本。任务很小、紧急或无法合理拆分时，Boss 可以直接处理，并记录例外和原因。

## 2. 角色与职责

| 角色或能力 | 责任 | 运行方式 |
|---|---|---|
| Boss | 管目标和优先级，定义验收，拆解派单，处理依赖与例外，核对关键证据并决策 | 常驻会话 |
| RSI | Boss 分析失败、吞吐和成本，委派有界研究并用独立实验验证 | Boss 兼任 |
| Watcher | 订阅本 Goal 的 swrm runs，批量去重汇报并续接 | 一个固定复用 subagent |
| Build lane | 根据 Issue、Spec 和验收标准实现并提交产物 | swrm 按需分发一条 build lane |
| Review lane | 独立审查固定版本，调度受控测试并汇总验收证据 | swrm 按需分发一条独立 review lane |
| 运维与诊断 | 主机、lane、服务和额度巡检，处理具体异常 | 自动巡检，异常时按需派任务 |
| 临时 subagent | 研究、资料整理、任务拆解辅助、结果汇总与局部排障 | 按需派任务，优先复用已有 agent |

Builder、Tester、Ops 的职责仍需覆盖，但不再调用历史平级聊天。独立审查、受控测试、巡检和异常处理必须由按需 lane/subagent 或工具覆盖，并通过真实任务验证。

## 3. Boss 异步工作

1. Boss 将可独立交付的工作写成任务卡，指定范围、基线、验收、预算和产物。
2. swrm lane 或临时 subagent 执行，完成后报告结果、证据与未解决事项。
3. 一个固定 watcher 使用 swrm 原生批量 watch，按显式 registry 订阅、以 cursor 续接；汇报成功后保存游标。Boss 按稳定事件 ID 去重并更新状态。不启用外部 bridge、信箱或 wait_threads。自动回执只确认消息已接收或入账，不代替 Boss 对结果的验收。
4. 常规进度合并汇报。任务完成、失败、风险和需要决策的事项及时送达 Boss。
5. Boss 核对关键原始证据、协调后续任务并作最终决定。测试消息使用隔离接收端，避免挤占 Boss 的工作队列。

## 4. 组件协作

| 组件 | 责任 |
|---|---|
| Phanes | 统一入口，管理目标、角色、任务生命周期和用户交互 |
| swrm | 调度作者与 review lane，跟踪运行状态并回收产物 |
| evalid | 记录测试命令、代码快照与运行结果，重放验证证据 |
| GitHub | 保存需求、代码变更、审查结论和项目状态 |

标准配置是每个需求由一条 build lane 实现，一条独立 review lane 负责对抗审查和验收。需求较大时可先拆成多个可独立验收的任务，再分别派发。

标准流程：

```text
Issue + Spec + 验收标准
          │
          ▼
Boss 拆解并通过 swrm 派发
          │
          ▼
build lane 实现并提交固定版本
          │
          ▼
独立 review lane 对抗审查
并调用受控测试执行器和 evalid
          │
          ▼
          Boss 核对结果并决定
                   │
                   ▼
          合入 PR，更新 Issue 和 Project
```

review lane 可以并行安排代码审查与受控测试。测试执行器和 evalid 通常以脚本或工具进程运行，不额外占用模型 lane。作者可以在开发中运行可见测试；验收阶段由独立流程控制固定版本、保留测试和证据。

完整 TDD 红绿证据必须从实现前开始记录。执行框架需要在作者动手前运行可见验收测试并保存红灯证据，在实现后记录绿灯并重放。对已完成且缺少红灯记录的任务，可以事后运行与重放测试，但不能据此声称已证明实现前的红灯过程。

Phanes、swrm 和 evalid 独立更新。记录已验证的版本组合，更新前检查兼容性，更新运行脚本后验证服务，并保留可执行的回滚路径。

## 5. 对抗审查与独立验收

每个实现 PR 分发给与作者独立的 review lane。审查输入包含 Issue、Spec、验收标准和固定版本的代码变更。审查重点是明确需求、正常行为、数据丢失或损坏、明显安全问题、测试覆盖和越界改动。

审查结果分为 BLOCKER 和 FOLLOW-UP：

- **BLOCKER**：违反明确验收条件，正常输入下崩溃或结果错误，数据丢失或损坏，或存在明显安全问题。解决并复核后才能合入。
- **FOLLOW-UP**：卡面未规定且不涉及上述后果的极端输入、额外边界测试、风格或可选优化。记录后续处理，不自动阻断当前交付。

review lane 调用受控测试执行器，在作者隔离环境之外运行保留测试和独立行为差分并记录结果。保留测试和证据由独立流程管理，作者无法改写。审查结论、测试结果和 evalid 证据分别保存，关联同一 Issue 与 PR。对测试和 Spec 冲突的情况，记录依据并交 Boss 决定。

评估通过率的实验应在运行前固定卡片、保留测试、真值、模型和统计口径。RSI 可以提出策略，但策略效果需要用独立数据验证。

## 6. GitHub 项目管理与追溯

GitHub Projects #6 和 #7 作为项目管理入口。实施前核对两个 Project 的实际用途、字段和状态流转，并确定跨项目映射。

### Issue 与 Spec

- 先有 Issue，再执行。Issue 至少写明目标与背景、实施范围、可验证的验收标准、关联 Spec、所属 Project 和必要依赖。
- 大需求拆成可独立实现与验收的子 Issue。Spec 链接到可识别的版本。
- 范围、验收或实现方向发生实质变化时，在 Issue 或 PR 中记录决定和原因。

### 执行留痕

- 每次派发关联 Issue，记录执行 lane、任务、代码基线、运行结果和产物位置。
- 测试命令、结果、evalid 证据及独立审查结论关联对应 Issue 或 PR。
- RSI 的策略变更记录假设、实验、结果和是否采纳。

### PR 与合入

- 每个 PR 必须关联 Issue。根据是否应在合入时关闭 Issue，使用 `Closes #编号` 或 `Refs #编号`。
- 每个 PR 必须通过独立对抗审查。BLOCKER 解决后由审查方复核。
- 验收针对固定的 PR 版本。后续改动影响已审查内容时，审查方复核新版本。
- Boss 核对 Issue 关联、当前版本审查结论和验收证据后决定合入，同步更新 Project 状态。
- FOLLOW-UP 有可追溯的后续处理位置。

## 7. 实施与验收顺序

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| 1 | 核对 Projects #6、#7，确定角色、状态和 Issue/PR 规则 | 一项需求能追到 Spec、任务、PR 和验收标准 |
| 2 | Boss 异步派作者与独立 review lane，收回固定版本及结果 | 一个真实任务完成派发、实现、独立审查和回收 |
| 3 | 在受控环境接入 evalid 和保留测试 | 同一产物的测试、重放和审查结果可追溯 |
| 4 | 接入 GitHub Issue、PR、审查及 Project 流转 | 真实任务从 Issue 到合入的记录完整，关联与审查条件得到执行 |
| 5 | 将 Builder、Tester、Ops 的稳定职责迁移到按需执行方式 | 真实任务证明自动分发、独立审查、异常处理和证据回收可用 |

各阶段先用少量真实任务验证，再扩大并发。当前提案描述目标架构，组件接口、独立运行边界和完整链路仍需逐项实现并验收。
