## 本轮 BLOCKER：真实的执行错误被摘要里的任务描述覆盖

复现（审查原文）：

```python
budget_failure({'status': 'failed', 'error_class': 'exec_error',
                'summary': 'Could not implement budget window exhausted handling: tests failed'})
# 修复前返回 True → finish() 挂起卡片而不是走 lane-failed，窗口恢复后还会错误重投
```

修复（`tools/lane-autodispatch/autodispatch.py` 的 `budget_failure`）：**明确的 `error_class`
优先**，摘要和 status 只能在没有 `error_class` 时作为线索。

- `error_class == "budget_exceeded"` → 预算窗口失败（挂起）。
- 任何其它明确的 `error_class`（`exec_error`、`rate_limit`、`budget_exceeded_daily` …）→
  真失败，维持原 `lane-failed` 流程。
- 没有 `error_class` 时，才按 `status == "budget_exceeded"` 或摘要里的预算措辞判断。

对应的测试（`tools/lane-autodispatch/test_budget_requeue.py`）：

- `test_exec_error_overrides_budget_words_in_the_summary`：摘要里写着 budget 措辞的
  `exec_error` 仍然走 `lane-failed`；状态重载 + 窗口恢复后也不会被重投。
- `test_non_budget_class_overrides_conflicting_budget_status`：`status` 与摘要都说预算、
  但 `error_class` 是 `rate_limit` 时走 `lane-failed`。
- `test_budget_hints_are_used_only_without_an_explicit_error_class`：没有 `error_class`
  时，status/摘要的预算线索仍然生效。

## B1：窗口仍耗尽时不得重投

真实执行器的 `result.json` 没有顶层 `resets_at`，所以固定的兜底延迟不够用。
`budget_window_open()` 在放行挂起之前必须**确认窗口已恢复**：

- 默认读 AD 状态目录里 health-loop 的 `health.json`：最多 900 秒旧，且必须**严格晚于**
  挂起时刻（`info["at"]`）；拿不到快照、快照太旧、快照不晚于挂起时刻 → 继续挂起。
- `AD_BUDGET_PROBE_CMD` 可以覆盖来源（运维探针）；探针按 lane/backend 选窗口，
  共享探针必须用 `{"lanes": {...}}` / `{"backends": {...}}` 指明目标。
- 未知窗口一律不放行；时间流逝本身不构成恢复证据。

测试：`test_the_card_stays_held_while_the_window_is_exhausted`（真实无 `resets_at` 的收割 →
挂起 → 推进 2 小时仍不重投）、`test_the_card_returns_to_the_queue_when_the_window_recovered`
（窗口恢复后自动回 `lane-ready` 并再次派发）、
`test_default_health_source_releases_only_after_both_windows_recover`、
`test_default_health_source_rejects_stale_or_unknown_windows`、
`test_default_health_source_requires_a_snapshot_after_the_hold`、
`test_probe_selects_the_target_lane_and_backend`。

## B2：预算失败次数跨重投保留

`_budget_failures`（按 issue 计数）与 `_budget_requeue`（挂起记录）都写在 AD 的 state 里，
重投时**只移除挂起记录，不清计数**；达到 `AD_BUDGET_REQUEUE_MAX`（默认 2）时按真失败收口。
终态（`lane-failed`、`lane-pr`、空产出）才清掉该卡的挂起与计数；终态标签写入失败时
**保留**记录，下一个 tick 重试，成功后才清理。

测试：`test_the_budget_failure_count_survives_a_requeue`（跨重投计数 ≥2、达到上限后收口）、
`test_the_bookkeeping_of_a_card_is_cleaned_up_when_it_leaves_the_hold`、
`test_terminal_label_failure_is_retried_after_state_reload`（两次标签写失败后重试成功）。
