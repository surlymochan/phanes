# PR #1803 本地审查入口（只依赖工作树里的普通文件）

前三轮审查的阻塞项都指向同一件事：**审查环境拿不到 diff**。

- `git fetch` 因 github.com DNS 解析失败（本轮复测仍然失败：`Could not resolve host: github.com`）；
- `gh pr diff 1803` 因未安装 `gh` 而不可用；
- 上轮还发现：文档里声称「上一轮头在本地对象库里可读」，但审查环境读不到；被指的 sha `1ef7b4866…` 在**本仓库**的对象库里其实读得到（`git cat-file -t 1ef7b4866` → `commit`），在审查环境读不到是因为那边的 `rebase-pr-1803` 还停在更早的头上。

本轮的做法：**不再依赖任何网络、任何对象库、任何外部命令**。审查需要的全部内容都以**纯文本文件**随 PR 进仓库，用 `read`/`cat`/`patch` 就能看，并配一个**离线自证**的命令（一条命令证明材料齐全、没被截断、证据与日志对得上）。

## 2. 一条命令自证（推荐先跑这个）

```sh
python3 tools/check-review-packet.py
```

输出形如（本仓库当前状态实测）：

```
head: <本轮头 sha>
manifest       ok    19 file(s) match the manifest
patch          ok    11 file block(s), 23 hunk(s), none truncated
patch-vs-git   ok    byte-identical to git diff 1ef7b4866..HEAD
heads          ok    18 blob sha(s) match the committed tree
evidence       ok    5 verdict row(s) match their shadow report
statistics     ok    the committed statistics match a fresh computation
```

它做六件事：

1. **manifest**：清单里每个文件都在，大小与 sha256 对得上（材料没被换掉、没被截断）；
2. **patch**：patch 的每个 hunk 都持有头部声明的行数——**被截断的 patch 会报错**，而不是被当成更小的 diff 读过去；
3. **patch-vs-git**：patch 与 `git diff <上一轮 head>..HEAD` **逐字节相同**（上一轮 head 不在对象库时这一项跳过并说明原因）；
4. **heads**：文件清单里的 blob sha 与已提交的文件树一致；
5. **evidence**：分歧日志里每个 `verdict` 行都指向一份**存在的**影子报告，且 PR 号、head、判定三者与该行一致；
6. **statistics**：仓库里的 `stats.json` 就是当前日志算出来的统计（重算一遍，不一致就点名）。

逐条命令（都不需要网络）：

```sh
python3 -m unittest discover -s tools/tests -p 'test_review_divergence_log.py' -v   # 20 项
python3 -m unittest discover -s tools/tests -p 'test_review_shadow_tester.py' -v    # 9 项
python3 -m unittest discover -s tools/tests -p 'test_check_review_packet.py' -v     # 10 项
python3 tools/review-divergence-log.py --self-test
python3 tools/review-shadow-tester.py --self-test
python3 tools/check-review-packet.py --self-test
python3 tools/review-divergence-log.py --log docs/evidence/review-divergence/divergence-log.jsonl stats
```

> **不要一次 `cat` 整个 patch**：审查报告会把长输出截断。要分段读：
> `sed -n '1,120p' .lane-review/PR-1803-round4.patch`，或
> `grep -n '^diff --git' .lane-review/PR-1803-round4.patch` 先看文件清单。

## 7. 提交与 force-push

**本车道的 git 元数据是只读挂载**（`/root/work/phanes-fleet/.git` 为 `ro` 挂载，`git add` 报
`Unable to create '.../index.lock': Read-only file system`），所以本会话**产生不了提交**：
提交与 force-push 由 AD 侧完成。工作树里已经是本轮修正后的完整内容，AD 侧按下面做：

```sh
cd <车道工作树>
rm -rf tools/__pycache__ tools/tests/__pycache__   # 别把字节码提交进去
git add -A
git commit -m "openswarm(pi): #1789 P1-3 tester 影子判定分歧日志基建：离线复核包 + 影子判定重跑 (Refs #1789)"
git branch -f rebase-pr-1803 HEAD   # 让审查环境断网也能读到本轮头（fetch 不到时它是唯一入口）
git push -f HEAD fleet/GH1-issue1789-20261103-040113-98ce97
```

push 之后，本轮头同时可以在 `rebase-pr-1803` 上读到（`git rev-parse rebase-pr-1803`），审查环境即使没有网络也能 `git cat-file -t <本轮头>` 与 `git diff <上一轮头>..rebase-pr-1803`。

> `rebase-pr-1803` 是审查环境拿到被审头的入口（dispatcher 用 `+pull/1803/head:refs/heads/rebase-pr-1803` 刷它）。
> 网络不通时那次 fetch 刷不动它，审查环境就会继续看上一轮的头——这正是前三轮「头读不到」的成因。
> 所以 force-push 之后请顺手把本地 `rebase-pr-1803` 指到本轮头。

> 车道里已经用一个**临时仓库**（`.openswarm-tmp/packet/`，已 gitignore）把本轮内容当成一次真提交跑过一遍：
> 上一轮头的树 + 本轮工作树 → `git diff --binary` 与 `.lane-review/PR-1803-round4.patch` **逐字节相同**；
> `python3 tools/check-review-packet.py --root .openswarm-tmp/packet --previous base-previous` **六项全过**。
> 所以 AD 提交后，审查环境里跑 `python3 tools/check-review-packet.py`（默认 `--head HEAD`）应当同样全过。

**本入口用于本地审查，不代表 GitHub 网络访问已恢复**：本轮复测 `git ls-remote origin` 仍然是 `Could not resolve host: github.com`。
